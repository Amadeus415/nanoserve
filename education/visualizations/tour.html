Room 1 · the idea

A restaurant with one stove.

Inference makes the next token. Serving is the restaurant around that stove: take the ticket, load the cookbook, time the work, stream the bites, and eventually share one counter among many tables.

The analogy to keep
The stove is the model. The cookbook is the weights — heavy, shared, it does not grow. The scratchpad of notes is the KV cache — it grows with every word of the conversation. The hallway to the pantry is memory bandwidth. You cannot write word five until word four exists.

Watch one meal leave the kitchen

client → server → engine → tokens

The server never generates a token. The engine never speaks HTTP. That seam is the whole design.

Room 2 · two paths

Dining room and test kitchen share the stove.

Both paths call the same engine and the same stopwatch. That is why a benchmark number is allowed to teach you about the server: nothing is hidden behind a different stack.

Why two doors
A diner cares about time-to-first-bite. A scientist cares about a grid of controlled meals. nanoserve keeps those as two front doors on one kitchen, not two products.

Same engine, two jobs

serving path · experiment path
Dining room curl / chat app → server.py → engine → SSE bites
Test kitchen bench.py → engine → one JSON line per meal → plot.py

Room 6 · streaming

Same kitchen. Two dining rooms.

The stove does almost the same work either way. Streaming changes when the diner is allowed to eat. Time-to-first-bite is a serving idea, not a model idea.

Cloche versus courses
Non-streaming is a silver cloche: the whole meal is cooked, then revealed. Streaming is sending each bite as it leaves the pan. The cooking time matches. The hunger time does not.

Room 7 · load, prefill, decode

Read the whole order. Then write one word at a time.

Load the cookbook once. Prefill is a parallel glance at the ticket. Decode is sequential: each new word needs the last one.

Three machines, one meal

Load

Put the cookbook on the counter. Expensive. Done once per process — not once per ticket.

→
Prefill

Process every prompt token together. Build the first stack of notes. Often compute-bound.

→
Decode

One forward pass. Append one note. Repeat. Word n+1 is locked until word n exists.

TTFT = start → first emitted token  ·  prefill_tps ≈ prompt_tokens / TTFT  ·  decode_tps = (output_tokens − 1) / (total − TTFT)

The first generated token sits inside TTFT, so decode speed counts only the later ones. prefill_tps is a useful approximation, not a kernel timer: TTFT also includes tokenize, Python, and that first decode step.

Room 8 · the workbench

One counter. A book that stays. Notes that grow.

On Apple Silicon the CPU and GPU share one pile of RAM. Weights are the cookbook: params × bits / 8. The KV cache is the scratchpad: it grows with every token and every open ticket.

Why decode feels like a hallway
Every decode step carries the entire cookbook plus every note so far through a finite door (~400 GB/s). A thinner book (quantization) or fewer notes (shorter context) makes each trip faster. That is why 4-bit is often quicker at decode, not only smaller.

Qwen3-14B uses grouped-query attention: 40 query heads share 8 KV notebooks. That is why its notes are 160 KiB per token, not 800.

Room 9 · the stopwatch

Name the intervals before you graph them.

A chart without a definition is decoration. These fields are what nanoserve actually writes down.

Two hungers
TTFT is how long until the first bite. Decode TPS is how fast bites keep arriving. total_s is the whole sitting. A diner feels TTFT first. A throughput graph brags about decode.

Model load is outside the sweep timer. The first real request can still include kernel compile. Three repeats show jitter; they are not a p95. Direct bench excludes HTTP, SSE, and the queue you have not built yet.

Room 11 · curriculum

Seven kitchens of increasing chaos.

Each lab is one question. The last two are not implemented yet — that is the point.

LAB 0

Mock pipeline

Can every waiter talk to the stove with plastic fruit?

LAB 1

Context length

Why does TTFT rise when the order gets longer? Prefill reads more. Notes pile up. Decode may slow as the hallway cargo grows.

LAB 2

Output length

Why is decode sequential? Hold the prompt still. Change the writing budget. Check output_tokens — EOS can leave early.

LAB 3

Memory

Predict with the scale, then measure process memory. The gap is the lesson: buffers, allocator caches, the formula’s omissions.

LAB 4

HTTP + stream

Same prompt three ways: direct engine, HTTP cloche, HTTP courses. Server TTFT vs client TTFT is serving overhead.

LAB 5

Concurrency

Four tickets, one stove. First make the line explicit. Watch head-of-line blocking. Then add one mechanism and rerun.

LAB 6

Quantization

Thinner cookbooks. Hold family, prompt, limit, temperature, and warm-up still. Quality needs a fixed eval set, not one summary prompt.

LAB 7

Another stove

Put llama.cpp behind the same engine interface. Remaining difference is implementation, not the model.

Lab 5 preview — one stove, four tickets

Today’s server stores one engine and only the last request’s stats. It has no queue, no continuous batching, no per-request history. Serialization with a visible wait is the highest-value next exercise — not a dashboard.

Room 12 · the locked door

A server that returns tokens is the core. It is not the whole subject.

Serving engineering also means scheduling, overload, tail latency, memory pressure, observability, and reliability. Keep the boundary honest so a mock curve never masquerades as a leaderboard.

Implemented now

  • Mock + MLX engines
  • OpenAI-style chat + SSE
  • Single-request timing
  • Memory estimator
  • JSONL sweeps + basic plots

Learning exercises, not claims

  • Warm-up-aware aggregation
  • Measured MLX memory
  • Client load generator
  • Queue and per-request metrics
  • Batching or prefix caching
  • Quality evaluation
  • llama.cpp backend

Room 13 · configuration

No config files. Labeled switches on the wall.

All server settings are NANOSERVE_* environment variables. Requests may override max_tokens and temperature. The model field is accepted for API compatibility; the loaded engine owns the actual cookbook.

Room 14 · common surprises

The kitchen will lie to you politely.

The first real ticket is slow

The cookbook may already sit on the counter. Kernels and allocator caches still warm up. Separate cold-start, first-request, and steady-state.

You asked for 1024 tokens and got 1,183

bench.py builds roughly that many words. The tokenizer decides. Analyze prompt_tokens, not only the target.

Fewer bites than max_tokens

The stove said EOS. The budget is a ceiling, not a promise. Use measured output count when comparing work.

The formula fits; macOS is sweating

The scale omits runtime overhead on purpose. Leave headroom. Shrink context or print a thinner book.

auto chose the mock engine

MLX-LM is not importable. On Apple Silicon: pip install -e ".[mac,viz,dev]"

The charts look official and came from plastic fruit

Put engine and model in the filename. Mock data validates plumbing. It does not describe this machine.
